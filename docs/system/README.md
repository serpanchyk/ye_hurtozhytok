# Система

## Як це працює

```text
Телефон (PWA: manifest, service worker, сповіщення)
        │  HTML-форми + React (гідратація)
        ▼
Cloudflare Worker ── React Router v7 (loaders / actions, SSR)
        │  Drizzle ORM          │ Cron Trigger щохвилини
        ▼                       ▼
Cloudflare D1 (SQLite)    нагадування через Web Push
        ▲
Google (OpenID Connect) ── вхід лише для акаунтів @lpnu.ua

https://ehurtozhytok.pages.dev ── Pages-шлюз (apps/gateway) ──► Worker
```

Один Worker віддає сторінки й обробляє форми, окремого API немає: кожен
маршрут має `loader` (читання) і `action` (зміни). Форми працюють і без
JavaScript. Стек і підходи ті самі, що в Опереті.

## Структура коду

```text
apps/web/app
  routes/               маршрути: loader читає, action змінює
  lib/booking.ts        правила запису (чисті функції, тести)
  lib/bookings.server.ts записи в D1, запис без гонок
  lib/auth.server.ts    сесії, вхід через Google, локальний вхід
  lib/google.ts         перевірка токена Google (домен lpnu.ua)
  lib/push.server.ts    підписки на сповіщення, надсилання
  lib/webpush.ts        Web Push без бібліотек (VAPID, aes128gcm)
  lib/scheduled.server.ts нагадування щохвилини
  lib/db/schema.ts      таблиці Drizzle
  components/           спільні елементи інтерфейсу
apps/web/public         sw.js, manifest, іконки
apps/gateway            Pages-шлюз для адреси ehurtozhytok.pages.dev
infra/d1/migrations     міграції, генеруються з db/schema.ts
```

Наступні частини (оголошення, дошка студради, оплата) — нові маршрути й модулі в `lib/`.

### Час

Запис зберігає київську календарну дату `date` (`YYYY-MM-DD`) і хвилини від
півночі за Києвом `start_min`, `end_min`. Тому «18:00» лишається 18:00 і після
переходу на літній час. UTC обчислюється з цього лише для нагадувань, через
`lib/time.ts`. Запис не переходить через північ. Моменти подій (створено,
скасовано) — UTC у мілісекундах, як в Опереті.

### Статуси запису

`active` або `cancelled`. Чи запис уже минув, видно з часу, окремо не
зберігається. «Звільнити раніше» переносить `end_min` на найближчу наступну
позначку кроку 5 хвилин від зараз.

Під оплату згодом додається статус `held` з `expires_at`: запис тримається
кілька хвилин, поки людина платить, а вебхук еквайрингу переводить його в
`active`. Тоді ж з’явиться таблиця `payments`.

## Запис і перевірка вільного часу

Правила (`apps/web/app/lib/booking.ts`, чисті функції з тестами; числа — константи там же):

- початок кратний 5 хв; тривалість від 30 хв до 2 год 30 хв з кроком 5 хв (`isDuration`); найдовший можливий запис від вільного початку дає `maxLengthAt`, найдовше вікно дня — `longestFree`;
- запис уміщується в години роботи (06:00–24:00) й не переходить через північ;
- між записами на одній пралці щонайменше 5 хв запасу;
- не більше 3 незавершених записів на людину; дата — сьогодні й ще 6 днів;
- сьогодні сервер приймає початок, що минув щонайбільше 10 хв тому, щоб не
  відмовляти сторінці, відкритій кілька хвилин тому.

**Вільні початки.** Для пралки й дня беремо активні записи, розширюємо кожен
на запас з обох боків і перебираємо початки з кроком 5 хв: підходить той, з
якого `[start, start + тривалість)` не перетинається з жодним розширеним
записом. Сьогодні — лише початки не раніше поточного кроку.

**Запис без гонок.** Перевірка й вставка — одна SQL-інструкція, тому двоє
людей не займуть той самий час навіть одночасно (D1 виконує записи послідовно).
Та сама інструкція перевіряє, що пралка працює, а людина не заблокована й
вказала кімнату (`lib/bookings.server.ts`, спрощено):

```sql
INSERT INTO bookings (machine_id, resident_id, date, start_min, end_min, status, created_at)
SELECT :machine, :resident, :date, :start, :end, 'active', :now
WHERE EXISTS (SELECT 1 FROM machines WHERE id = :machine AND status = 'working')
AND EXISTS (SELECT 1 FROM residents WHERE id = :resident AND blocked = 0 AND room IS NOT NULL)
AND NOT EXISTS (
  SELECT 1 FROM bookings
  WHERE machine_id = :machine AND date = :date AND status = 'active'
    AND start_min < :end + :buffer AND end_min + :buffer > :start
)
AND (SELECT count(*) FROM bookings
     WHERE resident_id = :resident AND status = 'active'
       AND (date > :today OR (date = :today AND end_min > :now_min))) < :limit;
```

Якщо вставлено 0 рядків, сервер з’ясовує причину (час зайняли, вичерпано
ліміт, пралка не працює чи акаунт заблоковано) і показує її людині.

## Вхід через пошту Політехніки

Пошта @lpnu.ua працює на Google Workspace, тому вхід — стандартний OpenID
Connect від Google (authorization code + PKCE), без паролів у нас:

1. `POST /auth/google` створює `state`, `nonce` і `code_verifier`, кладе їх у
   підписане httpOnly cookie на 10 хвилин і перенаправляє на Google з
   `hd=lpnu.ua`, `scope=openid email profile`.
2. `GET /auth/callback` звіряє `state`, обмінює код на `id_token` і перевіряє
   його підпис (JWKS Google), `aud`, `iss`, `exp`, `nonce`, а головне —
   `hd === "lpnu.ua"` і `email_verified`. Параметр `hd` у запиті лише підказка
   для екрана Google, тому перевірка на сервері обов’язкова.
3. Імʼя з каталогу Політехніки («Прізвище Імʼя По батькові») зберігаємо
   частинами; мешканці бачать «Імʼя Прізвище», студрада — повне ПІБ, а
   привітання бере імʼя в кличному відмінку. Мешканця шукаємо за `sub` (стабільний ідентифікатор Google), ім’я й пошту
   оновлюємо при кожному вході. Новий мешканець вказує кімнату й, за бажанням,
   ім’я користувача в Telegram.

Хто не увійшов, потрапляє на `/login?next=<сторінка>`, і після входу (через
Google, у тимчасовому cookie входу, або першого заповнення профілю) повертається
туди. `lib/next-path.ts` пропускає лише шлях цього застосунку: не інший сайт
(`//…`, `/\…`, `https://…`) і не сторінки входу.

Сесія — підписане cookie на рік з `resident_id` і `session_version`;
блокування збільшує `session_version`. Вхід, розпочатий у встановленій PWA на
iPhone, повертається в неї ж: перенаправлення в межах того самого вікна.

Для розробки: поки Google-клієнт не задано, на `localhost` з `DEV_LOGIN=1` на
`/login` є форма входу без Google (будь-яке ім’я й адреса @lpnu.ua). На
будь-якій іншій адресі або із заданим Google-клієнтом її немає.

Ризик: адміністратор Google Workspace університету може заборонити стороннім
застосункам вхід через акаунти @lpnu.ua. Перевірити до запуску; запасний план —
одноразовий код на пошту @lpnu.ua через Cloudflare Email Sending.

Вхід підтверджує, що людина з Політехніки, але не що вона живе саме в
гуртожитку №14. Це свідомий компроміс: ліміт записів обмежує шкоду, студрада
може заблокувати людину.

## Сповіщення

- Cron Trigger щохвилини (`* * * * *`) шукає записи, що починаються в
  найближчі 15 хв і ще не мають `reminded_at`, надсилає нагадування і ставить
  позначку, щоб не надіслати двічі. Запис, зроблений уже після цього моменту,
  нагадування не отримує.
- Коли студрада скасовує запис, людина отримує сповіщення; відправка йде у
  `ctx.waitUntil`, її помилки лише логуються й не ламають дію. Так само —
  про нову пропозицію оголошення (тим, хто вирішує) і про рішення (авторові).
- **Важливе оголошення всім** іде через чергу `push_outbox`: один
  `INSERT … SELECT` ставить у неї всі пристрої, перша порція йде одразу, решту
  щохвилинний cron забирає по 40 (`UPDATE … RETURNING`, тож два запуски не
  надішлють одне двічі) — так розсилка не впирається в ліміт підзапитів Worker
  (50 на безкоштовному тарифі). Кожне оголошення розсилається лише раз:
  перед розсилкою `UPDATE … WHERE broadcast_at IS NULL` ставить позначку, тож
  зняти й знову поставити «важливе» нічого не надішле.
- **Web Push**: ключі VAPID, шифрування повідомлень (RFC 8291) через WebCrypto
  прямо у Worker. Сповіщення вмикають у профілі для кожного пристрою. На iPhone
  вони працюють лише у встановленій PWA (iOS 16.4+), тому профіль показує, як
  додати застосунок на початковий екран.
- Поки що це єдиний канал. Запасні листи на пошту @lpnu.ua — після запуску:
  Cloudflare надсилає пошту лише з власного домену.

## Захист

- Підписки на сповіщення приймаються лише з адресами сервісів браузерів
  (Google, Mozilla, Apple, Microsoft), тож сервер ніколи не шле запитів на
  довільні адреси. На людину — не більше 5 пристроїв: найстаріші підписки
  видаляються.
- Дата, пралка, початок і тривалість запису перевіряються суворо ще до SQL.
- Нагадування спершу «займаються» одним `UPDATE … WHERE reminded_at IS NULL
RETURNING`, тож навіть два одночасні запуски cron не надішлють його двічі.
- Вихід видаляє підписку цього пристрою на сповіщення й кеш сторінок:
  браузер спершу очищає кеш, окремо від запиту про сповіщення, а сервер
  надсилає `Clear-Site-Data: "cache", "storage"` (саме `"storage"` очищає
  кеш service worker і працює навіть без JavaScript). Service worker зберігає
  для офлайну лише головну (`/`), оголошення (`/announcements`,
  `/announcements/:id`), «Послуги» (через них відкривається пральня),
  «Пральню» й сторінки пралок (разом з їхніми даними)
  та картинки `/media/*`, ніколи — «Моє», профіль, записи, форми, чергу
  пропозицій, студраду чи ролі.
- Заблокований мешканець може увійти й бачити профіль, але не записуватися;
  його ще не почати записи скасовуються в момент блокування. Поки людина
  заблокована, її ролі не діють (`isCouncil`, `isSquad`, `isSiteManager`
  повертають `false`): ні скасування чужих записів, ні списку мешканців, ні
  оголошень. Після розблокування ролі знову діють.
- Не більше 3 пропозицій оголошень на розгляді від однієї людини і не
  більше 5 за добу, забрані теж рахуються: кожна пропозиція шле сповіщення
  студраді.
- **Обмеження частоти дій** (`lib/rate-limit.server.ts`), щоб один акаунт
  скриптом не вичерпав денну квоту записів D1 безкоштовного тарифу для всіх.
  Кожна дія (не `GET`) проходить через `requireResident`, а там — не більше 10
  змін на хвилину на людину (Workers Rate Limiting, прив’язка `ACTION_LIMIT` у
  `wrangler.jsonc`) і не більше 300 записів людини в `activity_log` за добу.
  Понад це — відповідь 429 і сторінка «Забагато дій».
- Перед читанням картинок сервер перевіряє їхню кількість, тож запит із
  десятками файлів не заповнює пам’ять Worker.
- **Заголовки безпеки**: кожна відповідь має `X-Content-Type-Options: nosniff`,
  `Referrer-Policy`, `X-Frame-Options: DENY` і `Permissions-Policy`
  (`workers/app.ts`). HTML-сторінки в продакшені мають Content Security Policy
  (`lib/csp.ts`): скрипти лише з сайту або з nonce, який `workers/app.ts`
  створює для кожного запиту, а `entry.server.tsx` передає React Router;
  форми — лише на сайт і на вхід Google; вбудувати сайт у чужу сторінку не
  можна. У розробці CSP немає, бо Vite додає власні вбудовані скрипти.

## PWA

- `manifest.webmanifest`, іконки, `display: standalone`, світла тема.
- Власний невеликий `public/sw.js` (без `vite-plugin-pwa`, який погано
  поєднується з режимом фреймворку React Router): статичні файли — з кешу,
  сторінки — спершу мережа. Без мережі головна, оголошення, «Пральня» й сторінки пралок показуються
  в останній збереженій версії (дані сторінок `*.data` теж кешуються, тож
  опитування не ламає сторінку). Якщо такої сторінки ще немає в кеші, показується
  коротка сторінка «Немає зʼєднання» з кнопкою «Спробувати ще» й текстом
  помилки для розробника. Переходи на інші адреси service worker не
  перехоплює взагалі: їх веде браузер (на деяких телефонах перехоплені
  переходи падали, хоча інтернет був). Зміна правил кешу — нова версія `CACHE`.
- Записатися чи скасувати без мережі не можна: це завжди запит до сервера.
- Розклад оновлюється опитуванням раз на 20 с, поки вкладка видима.
- QR-наліпка на кожній пралці веде на її сторінку.

Жести (`lib/use-swipe-nav.ts`, у макеті сторінок): сенсорні події (не
pointer, щоб прокрутка браузера їх не скасовувала), свайп від 70 px, удвічі
пряміший за вертикаль, швидше за 0,7 с. На сторінках розділів меню —
сусідній розділ, від лівого краю (24 px) — «Назад»; обидва натискають
наявну вкладку чи кнопку «Назад», тож напрям і анімація ті самі. Жест не
починається на полях, `dialog`, картках дошки (`[data-task]`), елементах з
`[data-no-swipe]` і всьому, що гортається вбік.

## Текст оголошення

Подробиці зберігаються як Markdown. Пише їх візуальний редактор Tiptap
(`components/rich-editor.tsx`): жирний, курсив, підзаголовок, списки,
посилання. Він вантажиться лише в браузері на сторінці форми й кладе
Markdown у приховане поле `body`; без JavaScript — звичайне текстове поле.
Сервер перетворює Markdown на HTML (`lib/markdown.server.ts`, markdown-it):
HTML від людей лишається текстом, усі заголовки стають `h2`, посилання —
лише `http(s)`, `mailto:` і `tel:`, відкриваються в новій вкладці з
`rel="noopener noreferrer nofollow"`. Цитати, код, картинки й таблиці не
розмічаються. Картки на головній показують короткий текст без розмітки.

Час події — `<input type="time">` (рідний вибір телефона), сервер приймає
`ГГ:ХХ` будь-якої хвилини.

## Картинки

Картинки оголошень лежать у R2 (`MEDIA`, кошик `ehurtozhytok-media`) під
ключем `a/<id оголошення>/<uuid>.<розширення>`. Віддає їх Worker на
`/media/<ключ>` лише тим, хто бачить оголошення (`Cache-Control: private`,
ключ ніколи не змінюється) із заголовками `X-Content-Type-Options: nosniff`,
`Content-Security-Policy: default-src 'none'; sandbox`,
`Content-Disposition: inline` і `Cross-Origin-Resource-Policy: same-origin`.

- Телефон перемальовує кожне фото: до 1600 px по довшій стороні, рівно (з
  урахуванням повороту камери), новим JPEG без метаданих. Без JavaScript
  файл іде як є, до 8 МБ.
- Сервер визначає формат за першими байтами файлу (`lib/images.ts`), а не
  за тим, що каже браузер: лише JPEG, PNG, WebP; SVG, HTML тощо
  відхиляються, і зберігається визначений сервером тип.
- Сервер ще раз прибирає метадані: у JPEG — EXIF/XMP (APP1), інші APPn і
  коментарі (лишає JFIF, кольоровий профіль, Adobe); у PNG — `eXIf`, `tEXt`,
  `iTXt`, `zTXt`, `tIME`; у WebP — `EXIF` і `XMP ` разом із прапорцями у
  VP8X. Тож координати зйомки не потрапляють у сховище навіть без
  JavaScript (поворот такого фото тоді може загубитися).
- До 6 картинок. Видалене оголошення забирає й свої картинки зі сховища.
- Переглядач (`components/gallery.tsx`) відкриває картинку за адресою
  `#photo-N` поверх сторінки: «Назад» закриває його, а зміна лише цієї
  частини адреси нічого не завантажує (`lib/revalidate.ts`). Без JavaScript
  той самий переглядач відкривається через CSS `:target`.

## Права

Усі перевірки — у `lib/permissions.ts`, кожна дія перевіряє їх на сервері.
Кожен, хто увійшов, — мешканець; ролі (`council`, `council_head`, `squad`,
`squad_head`, `site_manager`) лежать у `role_grants` за поштою й додаються до
людини під час входу (`requireResident` повертає `roles`). Розпорядник має
права всіх ролей (`isCouncil` і `isSquad` для нього правдиві) і ще видає й
знімає ролі (`/residents`), крім власної ролі розпорядника. Студрада, голова
й розпорядник скасовують будь-які записи (на сторінці пралки) і бачать список
мешканців. Блокує лише розпорядник (`/residents`) — будь-кого, крім себе й
іншого розпорядника. Першого розпорядника призначає скрипт
`npm run role:grant -- --email імʼя@lpnu.ua --role site_manager [--remote]`.

Дошки: дошку студради веде студрада (`isCouncil`), дошку загону — загін
(`isSquad`), розпорядник — обидві (`canManageBoard`). Публічна дошка
(`/board`) однакова для всіх і лише показує; уся робота — на робочій
(`/work/board`, `/work/tasks/*`), куди пускає лише `canManageBoard`. Хто веде
дошку, бачить там приватні картки, подробиці, виконавців та історію, додає й змінює картки,
бере їх собі, перетягує між колонками (`lib/use-card-drag.ts`, той самий
запит, що й кнопки стану на картці) і передає на іншу дошку. Інші бачать
лише публічні картки: назву, місце, стан, дати й виконавців (`canSeeTask`). Видаляють автор картки, голова цієї
дошки й розпорядник (`canDeleteTask`); картку зі звернення не видаляють.

Звернення пише кожен незаблокований (`canWriteComplaint`); бачать його автор
і ті, хто веде дошку його картки, або розпорядник для звернень про
застосунок (`canSeeComplaint`, `canHandleComplaint`). Звернення йде за
карткою: передали картку на іншу дошку — його розглядає вже вона.

Вахти: стоять усі із загону (`canStandShift`); голова оперзагону й
розпорядник ведуть загін (`leadsSquad`): записують інших, змінюють і
видаляють будь-яку вахту. Решта змінює ті, що додали самі (`canEditShift`),
і звільняє свою (`canLeaveShift`). Взяти вільну вахту — один `UPDATE … WHERE
resident_id IS NULL`, тож двоє одночасно її не візьмуть.

## Секрети й налаштування

Секрети (`wrangler secret put`, локально — `apps/web/.dev.vars`):

| Назва                                      | Призначення                                    |
| ------------------------------------------ | ---------------------------------------------- |
| `SESSION_SECRET`                           | Підпис cookie сесії й тимчасового cookie входу |
| `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` | Вхід через Google                              |
| `VAPID_PRIVATE_KEY`                        | Підпис Web Push                                |

Відкриті значення — у `vars` файлу `apps/web/wrangler.jsonc`: `APP_URL`,
`VAPID_PUBLIC_KEY`, `VAPID_SUBJECT`, а також порожній `DEV_LOGIN`. Його
локально перекриває `DEV_LOGIN=1` у `.dev.vars` і вмикає форму входу без
Google; wrangler бере з `.dev.vars` лише оголошені в конфігу назви.
